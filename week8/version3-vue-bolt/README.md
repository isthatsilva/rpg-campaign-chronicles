# RPG Campaign Chronicles: Version 3 (Vue + Supabase, generated with bolt.new)

The same app as Versions 1 and 2, generated by **bolt.new** from `../bolt-prompt.md` and `../bolt-followup-prompt.md`,
then reviewed, tested and fixed with Claude Code. The code is exactly as Bolt exported it, apart from the manual fixes listed
below. Bolt exported into a `project/` subfolder; the files were moved up one level to match V1/V2, and Bolt's own short README
is kept as `README.bolt.md`.

| | |
|---|---|
| Frontend | Vue 3.4 (`<script setup>`, TypeScript) + Vue Router 4, built with Vite 5, Tailwind 3 + custom CSS |
| Backend | none of our own: **Supabase** (hosted Postgres + Auth + Row Level Security), called directly from the browser with `@supabase/supabase-js` 2.45.4 |
| Database logic | `supabase/migrations/202611020001_create_rpg_chronicles.sql`: tables, CHECK constraints, triggers, the `change_plan` function, RLS policies |
| Auth | Supabase Auth (email + password). Passwords are hashed by Supabase, and the session is kept in the browser |
| Tests | `npm run test:api`: 12 checks against the real Supabase project, plus a headless-Chrome click-through (13 checks) |
| Built with | bolt.new (free plan, without its Supabase integration), then Claude Code for review and fixes |

## How this differs from Versions 1 and 2

There is no Express or Flask server. The browser talks to Supabase directly, so **the database is the security boundary**:
- **Ownership:** Row Level Security policies on every table limit each user to their own rows. Child tables (attributes, equipment, journal) are checked through their parent character.
- **Plan limits:** a `BEFORE INSERT` trigger on `characters` locks the user's profile row, counts their characters, and raises `PLAN_LIMIT_REACHED` with SQLSTATE `42501`, which Supabase returns as **HTTP 403**. This plays the role of V1/V2's `BEGIN IMMEDIATE` count-and-insert.
- **Plan changes:** only through the `change_plan(new_plan_id)` function, which keeps history. Users can't write the `subscriptions` or `plans` tables directly.
- **Validation:** CHECK constraints in the database (lengths, ranges, real dates), mirrored by the Vue forms.
- **Signup:** a trigger on `auth.users` creates the profile and the Free subscription.

Other differences:
- ids are UUIDs
- a character's current health may be negative, but max health may not (same as V1/V2)
- the session lives in browser storage managed by Supabase, not in an httpOnly cookie

## Prerequisites

- **Node.js 18+** (developed on Node 26.11.1 / npm 11.20.0).
- A free **Supabase** project (supabase.com). The Supabase CLI and Docker are **not** needed.

## Setup

1. **Database:** in the Supabase dashboard, open **SQL Editor → New query**, paste the whole of
   `supabase/migrations/202611020001_create_rpg_chronicles.sql`, and run it. Re-running it is safe: it uses `IF NOT EXISTS`, `CREATE OR REPLACE` and `DROP ... IF EXISTS`.
   Then run `supabase/migrations/202611150001_backfill_dnd_defaults.sql` **once**. It gives existing characters with no attributes the six D&D defaults. On a brand-new project it does nothing, and it shouldn't be re-run later (it would refill characters whose owner removed every attribute).
2. **Auth settings:** in **Authentication**, turn off **Confirm email**, so registration signs you in immediately, and set the minimum password length to 8.
3. **Keys:** copy `.env.example` to `.env` and fill in:
   - `VITE_SUPABASE_URL`: your Project URL
   - `VITE_SUPABASE_ANON_KEY`: the **publishable** key (`sb_publishable_…`), or the legacy **anon** key

   Never put the service-role / secret key in this app. Tested with a publishable key.
4. Install:
   ```bash
   cd week8/version3-vue-bolt
   npm install
   ```

| `VITE_SUPABASE_URL` | yes | Project URL, e.g. `https://xxxx.supabase.co` (Project Settings → API Keys) |
| `VITE_SUPABASE_ANON_KEY` | yes | The **publishable** key (`sb_publishable_…`) or the legacy anon key. It's safe in the browser because RLS protects every table. Never the secret / service_role key. |

Vite only exposes variables that start with `VITE_`, and they are baked into the build, so restart `npm run dev` after editing `.env`.

## Tests

```bash
cd week8/version3-vue-bolt
npm run test:api
```

The 12 checks run against your real Supabase project **without the Vue app**, the way someone calling the API directly would:
- **Plan limit:** the 11th character on Free is rejected (`42501` / 403). **24 parallel inserts from a fresh account: exactly 10 succeed.**
- **Privacy:** another user can't read, update, delete or plant rows on someone else's characters, attributes, equipment, journal, profile or subscription. They also can't move their own row onto another user's character.
- **Signed out:** visitors only see the public plans.
- **Locked tables:** `subscriptions` and `plans` can't be written directly.
- **`change_plan`:** rejects unknown plans and the current plan, and keeps history. A downgrade keeps characters, blocks creates and still allows edits.
- **CHECK constraints:** reject empty or too-long names, negative level / max health / quantity, impossible dates and empty attribute values.
- **Attribute limit:** at most 50 per character.
- **Cascade delete:** deleting a character removes its attributes, equipment and journal entries.
- **Profile:** users can only change `display_name`, not their stored email.

Each run creates three throwaway accounts (`rcc.api.*@gmail.com`; no email is sent because confirmation is off). Delete them under **Authentication → Users** if you like.

**Not mutation-tested:** for V1/V2, I removed the lock on purpose to prove the race test can fail. Doing the same here would mean editing the live database's trigger, so it wasn't done. The race test passes, but it hasn't been shown to catch a missing lock.

The UI was also tested end-to-end in headless Chrome:
- a signed-out redirect
- register, with client-side password and confirm checks
- choosing a plan in a dialog with no input fields
- creating a character with level validation and a custom attribute
- equipment with quantity validation
- a journal entry
- **staying signed in across a reload**
- the account meter
- delete with confirm
- logout, wrong password, login
- phone width with no sideways scroll

All 13 checks pass. That script isn't part of this folder; see `../dev-log.md`.

## Manual fixes after generation (Claude Code)

1. **A reload while signed in sent you to the login page** (found by the browser test). `App.vue` and the router guard both call `loadAuth()`.
   The second call returned immediately because a `started` flag was already set, so the guard saw "no session" and redirected. Fix in
   `src/stores/auth.ts`: every caller awaits the same in-flight load promise.
2. **The page scrolled sideways on phones, and the 🌿/🔥 corner marks were never visible** (found by the phone-width check and by looking
   at screenshots). The two corner `<span>`s sat outside the positioned `.frame`, so they were placed against the page and ended up
   mostly off-screen; on phones the 🔥 stuck out 18px. Fix: moved them inside `.frame` (`App.vue`), added phone offsets, and set
   `overflow-x: clip` on `.app-shell` (`style.css`). Two earlier attempts using `overflow-x: hidden` didn't work: one was on an element that
   isn't the corners' containing block, and on `body` it still left the page 18px wider than the screen.
3. **Users could overwrite the email stored on their own profile** (found by `test:api`). Bolt's `GRANT UPDATE(display_name)` didn't restrict
   anything, because Supabase already grants authenticated users UPDATE on every column of new tables. Fix: `REVOKE UPDATE` on the table
   first, then grant `display_name` only (appended to the migration).
4. Added `tests/api-check.mjs` and the `test:api` script.
5. **Feature change (my request, 2026-11-15):** the create form starts with the six D&D attributes at 10, which the user can change,
   remove or add to (`CharacterEditPage.vue`). Existing characters with no attributes were backfilled once with
   `supabase/migrations/202611150001_backfill_dnd_defaults.sql`.

## Known issues / limitations

- A character with no health entered shows "0/0 vitality", and an empty level shows "LVL 0". Bolt displays null as 0 (V1/V2 hide empty stats).
- Health is validated as "0 or more" in the form, although the database (like V1/V2) allows negative current health.
- On the dashboard at exactly the plan limit, the Create button turns into a link to `/plans` without saying why. V1/V2 show a sentence explaining it. The over-limit warning banner does work.
- Creating or editing a character and its attributes is not atomic: the character is saved first, then its attributes. If the second step fails, the page says so, but the character stays saved.
- The 50-attribute limit isn't locked against simultaneous inserts, so parallel requests could slightly exceed it (unlike the plan limit).
- Deleting an attribute uses the browser's `confirm()` dialog instead of the styled modal.
- On the character profile, the custom-attribute rows and the Edit/Delete links on journal entries are unstyled ("Sanity ShakenEditRemove" runs together, and the add-attribute inputs show as a plain bar). Root cause: Bolt's markup in `CharacterDetailPage.vue` uses the classes `inline-record`, `inline-add` and `record-actions`, but `style.css` has no rules for them. Found in the Phase 4 screenshots (`docs/screenshots/profile-overview.jpg`). Everything still works; it only looks wrong.
- No password reset, login rate limiting beyond Supabase's defaults, or account deletion (same scope as V1/V2).
